### Identity, backend and feature boundaries

- One account across Android and the website. Reuse Clerk identities, Cloudflare Worker APIs, existing storage/coordination and Keyo entitlements where applicable.

- The model used to build the app does not determine which models Taskitator offers to end users. No automatic Light/Smart/provider redesign.

### Offline personal work

- Personal task creation, edits, deletion and non-audited completion work offline, subject to existing protection rules. Offline is not permission to remove audit protection or bypass shields through editing, deletion or import.
- Projects, calendar, statistics, personal import/export and applicable settings work on locally available data. Show whether cloud changes remain pending.
- AI calls are unavailable offline. Clearly explain why an audited task cannot be normally completed offline; preserve the existing explicit Emergency Bypass path.
- Persist pending operations across process death and reboot, partition by account, and never replay one account's data as another.
- Conflict resolution must preserve user work. The device's wall-clock timestamp alone must not choose a winner.

### Pro and time

- Persist login; do not force a fresh login at every launch or entitlement refresh.
- Server-signed Pro pass: stable account ID, issue time, subscription expiry, pass expiry, version/key ID and relevant feature claims. Email/username are display metadata, not authority.
- Offline validity ends at the earlier of seven days since verification and the subscription's actual expiry. For a verified non-expiring subscription, the seven-day limit still applies.
- Refresh automatically when authenticated online verification succeeds; rate-limit/debounce refreshes instead of checking on every screen tap. A failed refresh cannot extend expiry.
- An expired offline pass falls back to Free without deleting existing user work. Server-backed Pro operations still have server checks.
- Use verified server time and elapsed time, persist a time anchor, and handle reboot, clock changes and timezone changes. Suspicious/uncertain time can require reconnection for time-sensitive grants; ordinary Free personal work remains accessible.
- Offline revocation cannot be immediate; local tampering cannot be made impossible. Never claim otherwise.

### Bypass accounting and app exemptions

- Enforce each device's cached available allowance offline. Usage is recorded durably and reconciled into the shared online account allowance.
- All offline devices may independently spend their cached allowance. The user explicitly accepts aggregate overspending before synchronization.
- Example: allowance 4/week; A spends 2 and B spends 2 → cloud 4 used, 0 remaining. A spends 4 and B spends 4 → cloud 8 used, 0 remaining. Do not discard excess events or invent a negative next-week debt without a new decision.
- Each spend has a unique ID, installation/device ID, account ID and allowance-period ID. Retries count once. After syncing, update the local snapshot from the server. Going offline again must not replenish an allowance.
- Recommended snapshot rule: a device starts with the last server-confirmed remaining allowance, then subtracts its own not-yet-reconciled spends. It does not reset to the full weekly allowance on every refresh, reinstall or connectivity change. Resolve first-install and long-offline rollover behavior in Phase 1.1.
- Each token permits up to **three distinct app exemptions**, excluding strict apps. Persist the chosen apps; do not permit rotating unlimited apps through the three slots.
- Exemptions end at the user-configured end of day, automatically rejoining the effective blocked list next cycle. The underlying saved list is unchanged. Explain expiry before spending and notify when blocking resumes.
- Proposed safeguard: snapshot each granted exemption's cycle and expiry; later end-of-day changes cannot extend it. Do not confuse the daily exemption end with the allowance's weekly reset.
- Existing task bypass and new app exemption behavior must have an explicit charging contract. Do not assume one app exemption automatically completes an AI task or silently charges a second token. Resolve this integration in Phase 1.1 using existing behavior and the user's direction if ambiguous.

### Native app blocking

- Only user-selected apps. Optional social suggestions are opt-in.
- No whole-phone lock, replacement launcher, persistent full-screen blocker or new lock-screen interface.
- Detect a selected foreground app, use supported dismissal/Home behavior, and show a brief task reminder. Start with notifications; optional on-top alerts need explicit consent and applicable special access.
- Exclude emergency calling, default dialer, critical system components, Settings/permission controls and Taskitator. Keep the route to completing tasks and submitting evidence usable. Detect essential roles dynamically; do not rely only on one vendor's package names.
- Blocked-list changes inside Taskitator are restricted while applicable work is outstanding; app exemptions are temporary rather than permanent list removals. Resolve whether users may also add blocks mid-cycle without weakening the rule.
- Optional strict mode: selected apps cannot be exempted through Emergency Bypass. Recommended activation/change rule: configure before the cycle; stricter changes take effect next cycle. Strict mode cannot prevent system permission revocation or uninstall.
- Do not obstruct Android Settings to prevent bypass. A normal productivity app is not enterprise device management or parental control.
- If personal and Universe reasons affect the same app, track them independently. Suspending one reason must not clear another valid block.

### Universe

- Universe data and actions are unavailable without a working server connection; no offline Universe mutation queue or offline browsing mode.
- Suspend Universe-derived blocking when disconnected/unreachable. Personal blocking continues independently.
- On reconnect, fetch current authorized state before resuming Universe access or blocking. Membership removal, owner changes and task completion may have occurred elsewhere.
- Connectivity detection has a finite delay: use actual API reachability, bounded timeouts and a foreground health policy; a Wi-Fi icon alone does not prove server access. Do not promise instantaneous loss detection.
